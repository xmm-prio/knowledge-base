# 中文检索走网关自建的 jieba 分词索引

文档检索不用 basic-memory 的搜索，改由网关自己维护一份 SQLite FTS5 索引，入库前用 jieba 对中文分词。索引放在 `.knowledge-base/` 下，随时可删可重建。

原因是 basic-memory 的 FTS5 建表语句把 `tokenize='unicode61'` 写死在源码里，而 unicode61 把汉字归类为字母数字字符，**一整串连续汉字会成为一个没有内部边界的 token**。加上它自动补的前缀通配符，中文检索实际退化为「子句级前缀匹配」：查询词必须正好落在某个汉字串的开头才命中。实测一组中文技术文档，搜「对齐」三篇里只命中一篇（另外两篇的「对齐」在句中），搜「脏数据」「尾块」「双缓冲」**一篇都命中不了**。技术文档的关键术语通常在句中，这是系统性失效。

jieba 预分词后同一组查询全部精确命中，分词开销 0.076 ms/句，纯 Python，不需要原生扩展也不需要下载模型。

## Considered Options

- **FTS5 trigram 分词器**：实测无效。trigram 要求匹配串至少 3 字符，而「对齐」「尾块」这类 2 字术语正是核心用例。
- **ICU 分词器或 `wangfenjin/simple` 扩展**：都要改 basic-memory 的建表语句，违反 ADR-0001。
- **在 Markdown 文件里插空格预分词**：技术上可行且不用改上游，但源文件不再是给人看的中文，直接否决。
- **中文 embedding 模型**：basic-memory 内置向量检索，改几个环境变量即可切到 `BAAI/bge-small-zh-v1.5`。能解决问题，但引入模型下载与推理开销，且它做的是语义召回而非精确匹配。

## Consequences

- basic-memory 保留，但**只负责关系图谱、WikiLink 解析与上下文遍历**，不再是检索的执行者。它仍会索引一遍全部文件，这份重复开销是接受的代价。
- 观察级检索由我们自己实现。这反而更顺手——网关本来就要解析语义 Markdown。
- **语义检索没有上**。搜「尾块数据不对」找不到「读到脏数据」，因为 jieba 是精确匹配。这是明知的缺口，不是遗漏；补它只需打开 basic-memory 的向量检索并换成中文模型，不需要重构。
- jieba 的词典决定切分质量。领域术语（如「双缓冲」「尾块」）切错时，靠自定义词典修正，不改索引结构。
