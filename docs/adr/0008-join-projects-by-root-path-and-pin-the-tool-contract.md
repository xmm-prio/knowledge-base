# 用 root_path 关联上游项目，并把它的工具契约固定进测试

上游的每个读取工具都把 `project` 列为必填，而它给项目起的名字是**索引时那条路径打平**的结果：`/home/mdc/mops-knowledge-base/codebase/ops-nn` 被记成 `home-mdc-mops-knowledge-base-codebase-ops-nn`。这个拼法没有文档，也不是我们能复现的——它取决于上游当时拿到的是哪条路径。

我们曾按目录名去比对、去当 `project` 传。结果是：已经建好索引的代码库在页面上一律显示「未索引」，而每一次限定仓库的检索都换回一句关于缺少参数的拒绝。**改为按 `list_projects` 一并返回的 `root_path` 与磁盘目录对上号**：目录就是目录，这个关联对既有索引与将来新建的索引同样成立，不需要重建任何东西。

同一轮里还发现 `search_code` 的入参叫 `pattern`（我们一直在传 `query`）、`search_graph` 与 `trace_path` 默认回的是**文本树**而非 JSON、分页不传就静默截断在 50 条、以及判断「能不能查」本有 `index_status` 这个专门的工具。这些都不是罕见路径上的疏漏，而是这一层从头到尾**照着猜的接口**写成的——测试替身对参数来者不拒，于是五百多个通过的用例在这个接缝上什么都没证明。

因此第二个决定：**上游的工具契约以 `tests/upstream_schema.py` 的形式固定下来**，逐字抄自安装在部署机上的二进制的 `tools/list`。假通道据此作答——缺必填参数就按二进制的原话拒绝，出现该工具没有的参数就记一笔违约、由 autouse fixture 判当次测试失败。

第三个决定与此同源。参数错了会被拒绝，**回答的形状猜错了却是静悄悄的**：上游 `format: "json"` 回的是一张列式的表——`cols` 给列名，行是数组，`groups[].qn_prefix` 加行内的 `name` 才拼得出限定名——而我们的解析在找 `{"results": [{"qualified_name": ...}]}`。两者都不报错，只是一条都读不出来。同一个 `search_graph`，问 `name_pattern` 与问 `query` 回的还是两种表；`search_code` 干脆没有 `format` 参数，只回文本报告。因此**解析一律以实测报文为准，实测报文逐字存进 `tests/upstream_replies.py`**，解析器的测试跑在这些真报文上。

`trace_path` 的形状还改变了一个结论。它给的是每一跳**距离起点多远**，以及该跳是怎么解析出来的（`lsp` / `language_rule` / `heuristic` / `unresolved`），**不给边**：第二跳经由谁抵达，报文里没有这个信息。所以「只保留能唯一确定的关系」在这里落到两条上——`unresolved` 的跳只计数不呈现，第 2 跳起不画符号之间的连线。

## Consequences

- 目录名与项目名是两个不同的概念，`CONTEXT.md` 分别收了词条。`Scope` 把两者绑在一起传递，越过这一层之后不应再出现目录名。
- 一次问答要先读一遍 `list_projects`。这是本地调用，代价可接受；换来的是列表与由它推出的答案必然自洽。读取失败时，「列出代码库」容忍（全部显示为未索引），「回答问题」不容忍（上游不可用与尚未索引是两件事，混为一谈会把人支去做无用的索引）。
- 不指定代码库的检索由网关**逐个问一遍**再按代码库先后排开，不做跨库排序：相关度是各库各自算的。`query_code_graph` 无法这样兜底，改为必须指定代码库。
- 上游升级后必须重新读一次 `tools/list` 更新 `tests/upstream_schema.py`，并重新采一遍报文更新 `tests/upstream_replies.py`，否则固定住的是上一版。这两步都写在发布前的真实上游门禁里。
- 报文形状变了，替身仍会照旧作答，一切照绿——所以门禁里另有一组用例，拿真二进制的回答检查**解析出来的结果**（读到了、`raw` 为空、`unreadable` 为零），而不是检查报文本身。
- 判断「已索引」的同一次 `index_status` 调用顺带给出图的规模与未完整解析的文件数，这些一并呈现在代码库列表上：既然为它付了代价，就不该丢掉。
- 二进制对不认识的参数是静默忽略的，所以拼错一个参数名在生产上没有任何回声。测试替身比二进制更严格正是为此。
